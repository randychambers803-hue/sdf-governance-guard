EXECUTIVE SUMMARY

SDF Governance Guard — From Signal to Governed Action

Discipline Consulting Group LLC × Dynatrace · Dynatrace MCP Challenge Submission

Every AI agent that touches your infrastructure needs to know three things before it acts: what happened, how serious it is, and what it's allowed to do. Without answers to all three, agents guess. And when agents guess in production environments, they create the exact problems you deployed them to prevent.

SDF Governance Guard solves this with a three-word classification system — Signal, Defect, Failure — that turns every observability event into a governed action. The classification is the boundary. It determines what an agent can see, what it can do, and what evidence it must leave behind.

This application walks you through five stories that show how Governance Guard works — from a single event detection through enterprise-scale continuous authorization. Each story builds on the last. By the end, you'll understand not just what Governance Guard does, but why it works the way it does and what it means for your authorization posture.

This is not a prototype. It is a platform standard — built on Dynatrace's Compliance Assistant, Davis AI, Model Context Protocol, and Grail — and submitted as a complete solution to the Dynatrace MCP Challenge.

"The classification of the data determines the permission of the agent."
HOW IT WORKS · A PLAIN-ENGLISH GUIDE

The Three Building Blocks

SIGNAL · DEFECT · FAILURE — THE CLASSIFICATION SYSTEM

SDF stands for Signal, Defect, Failure. These are the only three states a compliance event can be in. A Signal means something changed — watch it. A Defect means something is degraded — investigate it. A Failure means something broke an authorization boundary — fix it immediately, with guardrails. This single classification is the only thing that determines what any agent is allowed to do next. That's the whole system.

GOVERNANCE GUARD — THE ENFORCEMENT LAYER

Governance Guard sits between the detection system and the agents. Nothing gets to an agent without passing through it. When an event arrives, Governance Guard reads its classification, looks up what the pre-approved policy says about that classification, and either authorizes the action, restricts it, or blocks it entirely. Every decision is logged immediately and permanently. There's no override, no workaround, and no configuration that lets an agent skip the gate.

The Three Boundaries That Matter

Select a boundary to see exactly what passes through it — and what doesn't.

What the Detection Layer Passes to the Normalization Layer

Compliance Assistant produces one thing: a raw detection event. Risk level, system ID, timestamp. That's it. It doesn't classify the event. It doesn't decide what to do about it. It detects and hands off.

MCP takes that raw event and turns it into the structured payload that Governance Guard can actually use. It adds the classification tier, the policy references, and the lineage ID. From this point forward, every system in the pipeline works from this package — not the original alert.

KEY PRINCIPLE

Detection and normalization are separate jobs on purpose. The Compliance Assistant doesn't need to know how MCP works. MCP doesn't need to know how detection works. Separation is how you keep the system auditable.

PRIMARY INTEGRATION SURFACE
What the Normalization Layer Passes to the Enforcement Layer

Governance Guard never reads the raw detection event. Ever. It only reads the normalized package that MCP built. This is the most important boundary in the system.

When Governance Guard receives the package, it reads one field first: the classification tier. That field determines the entire enforcement policy. FAILURE means remediate with guardrails. DEFECT means investigate only. SIGNAL means observe only. The other seven fields are supporting evidence — important for the audit record, but the classification tier is the decision.

KEY PRINCIPLE

Nothing unclassified ever reaches Governance Guard. That's not a policy — it's an architectural guarantee. There's no path for raw data to get through.

What the Enforcement Layer Passes to the Action Layer

Agents don't receive raw events. They don't receive the MCP package either. They receive exactly one thing: the governed result from Governance Guard. That result tells them what they're authorized to do — and nothing else.

A FAILURE classification authorizes the remediation playbook — that playbook, nothing else. A DEFECT authorizes investigation only. A SIGNAL authorizes observation only. An agent has no way to expand its own permissions. That limit is built into the architecture, not configured in a settings file somewhere.

KEY PRINCIPLE

The permission boundary is architectural. No configuration change, no prompt engineering, and no runtime override can move it.
